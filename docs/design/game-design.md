# Dream of One - Design Bible (LLM-First)

## 0) Design statement
Dream of One is a social stealth simulation where the world behaves like a small society. NPCs are autonomous LLM agents with organization-specific norms. The player must stay procedurally normal to avoid being identified as lucid.

Terminology note: use canonical terms from `terminology.md` in design and runtime-facing copy.

## 1) Experience goals
- The player should feel social pressure, not combat pressure.
- NPCs should appear to have intent, memory, and organizational context.
- Each session should produce different social trajectories without adding system complexity.
- Failure must feel explainable, not arbitrary.

## 2) Pillar-to-feature mapping
- **LLM agency first** -> NPC action decision loop uses LLM for most non-trivial actions.
- **Readable causality** -> every major escalation writes a why-line.
- **Small system, deep behavior** -> action set stays fixed; variation comes from context and memory.
- **Dream-cover pressure** -> the player's risk comes from social interpretation and reports.

## 3) Core entities
- `Player`: only lucid dreamer, low verb count.
- `NPC Agent`: role-bound LLM actor with memory.
- `Organization`: local policy and procedural expectations.
- `Artifact`: record object generated by social process.
- `Station`: formal escalation and closure authority.

## 4) Minimal action language (NPC)
Allowed actions in v0.1:
- `Move`
- `Talk`
- `Ask`
- `Observe`
- `Work`
- `Report`
- `Escort`
- `Idle`

No other action types are allowed in runtime decisions.

## 5) Player interaction language
Player speech acts:
- `SA_COMPLY`
- `SA_INQUIRE`
- `SA_FRAME`
- `SA_BREAK`

The player does not need free-form command systems in v0.1.

## 6) Agent cognition model
## 6.1 Identity memory
- role title
- organization
- authority boundaries
- default tone and risk tolerance

## 6.2 Episodic memory
- compact rolling window of recent observed events
- last interactions with player and key NPCs

## 6.3 Social memory
- trust/suspicion score toward known actors
- recent cooperation or conflict traces

## 6.4 Memory persistence policy
- Per-NPC memory is file-backed in the Actor Workspace (`data/workspaces/<sessionId>/<npcId>/`).
- Long-term Facts are persisted in `MEMORY.md`.
- Daily episodic logs are append-only in `memory/YYYY-MM-DD.md`.
- Promotion policy favors durable social facts, especially player suspicion trends.
- Runtime integration is implemented in `DefaultCodexBroker.recordWorkspace(...)` with `FileActorWorkspaceStore.appendNpcMemory(...)`.

## 7) Organization behavior specifications
## Store
- Prioritizes order and procedural phrasing.
- Sensitive to queue and compliance deviations.

## Studio
- Prioritizes approval process and documented changes.
- Sensitive to unapproved actions and meta-dismissive language.

## Park
- Prioritizes observation etiquette and public calm.
- Sensitive to probing and destabilizing behavior.

## Station
- Prioritizes formal intake and report evaluation.
- Converts social suspicion into formal escalation.

## 8) Session choreography (10-12 min)
- `0:00-1:00` brief + checklist
- `1:00-8:00` active society + player cover work
- `8:00-11:00` report/intake pressure zone
- `11:00-12:00` ending resolution

## 9) Escalation mechanics
- NPCs observe anomalies and may discuss/report.
- Reports produce artifacts.
- Station intake aggregates context and evaluates exposure risk.
- `Lucid identified` ends session immediately.

## 10) Artifacts and explanation model
Minimum artifacts for v0.1:
- witness statement
- report memo
- station intake record

Every major outcome should include:
- triggering event summary
- witness or source
- resulting artifact reference

## 11) LLM usage policy
- Codex CLI is the default NPC cognition engine.
- Runtime orchestration is implemented directly in repo-owned Codex control plane (no external Agent SDK mediation).
- LLM output must follow strict schema.
- Invalid response results in fallback action.
- Minecraft Server remains execution authority via Mineflayer Bot commands.

## 12) Technical runtime map
- Mineflayer Bot emits observation packets (`blockUpdate`, `entitySpawn`, `diggingCompleted`, lifecycle events).
- TypeScript backend orchestrates NPC sessions and calls Codex (`codex`, `codex-reply`).
- Mineflayer adapter validates and executes Bot Commands (`bot.dig`, `bot.placeBlock`, `bot.activateBlock`, `bot.updateSign`).
- Runtime telemetry and Evidence Pack outputs store outcomes.

## 13) UX requirements
- HUD shows current suspicion/exposure pressure.
- Player sees immediate reason hints after risky interactions.
- End screen summarizes why outcome occurred.

## 14) Tuning guidance (keep simple)
- Tune by adjusting:
  - active NPC count
  - update cadence
  - escalation thresholds
- Do not tune by adding new gameplay systems.

## 15) Anti-bloat rules
- No economy/combat/progression for v0.1.
- No new organization beyond 4 landmarks.
- No expansion of NPC action set beyond 8 actions.
- No additional player verbs beyond speech acts + interactions.

## 16) Validation checklist
A candidate build is valid if:
- NPC society runs autonomously for 5 minutes.
- player loop can be completed in 10-12 minutes.
- at least one coherent social escalation trajectory appears in normal play.
- failure/survival reason is readable.
- LLM-off fallback run remains playable.

## 18) Trajectory diversity verification procedure
### Goal
- Verify that repeated runs produce non-identical social trajectories while staying inside the bounded behavior Specification.

### Procedure
1. Execute at least three consecutive runs for the same scenario setup and Runtime Path configuration.
2. Capture per-run Evidence from:
   - `/v1/telemetry/evidence-pack`
   - `/v1/telemetry/events?limit=200`
   - social process outputs shown to the player
3. Compare trajectory markers across runs:
   - witness/source composition in report artifacts,
   - rationale wording and Reason Category distribution,
   - outcome path (`survival`, `escalation`, `lucid identified`) and timing.
4. Confirm bounded rules remain unchanged:
   - NPC action whitelist from Section 4,
   - player speech acts from Section 5.
5. Record findings in `docs/design/ws8-final-migration-report.md`.

### Acceptance Criteria
- Three-run set contains at least one meaningful trajectory delta in social process outputs.
- Every run preserves readable cause-effect social trajectory in player-visible outputs.
- No run violates the bounded behavior Specification.

### Validation Criteria
- Migration report links each run to reproducible Evidence artifacts.
- If diversity is insufficient, add a residual risk item to the WS8 backlog instead of forcing synthetic variation.
