# Dream of One - Project Definition (Minecraft Intent-First v10)

## 0) One-line definition
A Minecraft social-stealth simulation where NPC society pressure is generated by stateful Codex-driven Mineflayer bots and executed through deterministic world rules via a TypeScript backend.

## 1) Product goal (fixed)
Ship a playable v0.1 slice where the player survives by doing cover work under social scrutiny.

### Primary evaluation question
In Minecraft runtime play, does a Codex-driven NPC society actually run the pressure loop against the player?

This question is primary.
Platform/framework detail is supporting.

## 2) Core product promise
- Player is not an investigator.
- NPCs and institutions investigate the player.
- Text and social procedure are the danger surface.
- End-state rules remain deterministic and testable.

## 3) What matters most (priority order)
1. Minecraft session loop runs end-to-end for 10-12 minutes.
2. NPC social actions are generated by Codex cognition path in live loop (target >= 70% non-idle).
3. NPC autonomy continuity is stateful by bot (`npcId`) with session continuity across `login` -> `spawn` -> `respawn` lifecycle events.
4. Runtime remains stable under load (bounded Codex execution, no process explosion stalls).
5. Report -> intake -> verdict closure is understandable to player.
6. Nearby NPC behavior changes are directly observable in world state and structured runtime evidence.
7. Codex failure never stalls progression (deterministic fallback).

## 4) Technical architecture (supporting, not primary)
### 4.1 Chosen stack for v0.1
- Runtime client: Mineflayer (`/Users/user/git/gigio1023/mineflayer`) on Minecraft Java server sessions.
- Backend runtime: Node.js 22 LTS baseline (`>=22` minimum).
- Backend server: TypeScript runtime API (current implementation: Node HTTP server).
- Backend language: TypeScript 5.9.
- Agent orchestration: repo-owned direct Codex runtime control plane (no external Agent SDK mediation).
- NPC cognition engine: Codex CLI (`codex`, `codex-reply`).

### 4.2 Runtime model (authoritative)
- NPC logic model: one logical bot state per `sessionId+npcId` (not one always-running OS process per NPC).
- Continuity model: Codex session continuity via `codex exec` -> `codex exec resume`, synchronized with Mineflayer lifecycle events.
- Memory model: bot-scoped Actor Workspace data is durable and queryable, with game-specific file layering:
  - `MEMORY.md` (Long-term Facts),
  - `memory/YYYY-MM-DD.md` (append-only episodic logs),
  - runtime JSON artifacts (`persona/policy/memory/summary/thread`) for deterministic transport state.
- Memory policy is simulation-oriented: preserve natural NPC continuity and durable player suspicion signals, without enforcing a fixed internal thought pipeline.
- Execution model: bounded Codex worker pool + per-NPC action queue with one in-flight action to prevent unbounded child-process fan-out.
- Failure model: timeout/tool/parse errors fall back deterministically without freezing the simulation.

### 4.3 Authority boundary
- Minecraft server authority: world observation truth, action validation, end-state rule enforcement.
- Mineflayer adapter authority: lifecycle/event ingestion and bounded action execution against Minecraft APIs.
- Backend authority: NPC intent brokerage, session continuity state, strict Schema validation, and policy enforcement.
- Codex authority: propose intent only (no direct world mutation).
- Safety authority: deterministic Fallback Path when parse/tool/timeout/runtime failures happen.

### 4.4 Runtime guardrail (direction lock)
- v0.1 critical runtime path must not depend on external Agent SDK orchestration.
- External SDK research/docs may exist, but acceptance evidence must come from direct Codex + Mineflayer runtime path.

## 6) Non-negotiable constraints
### 6.1 Scope constraints
- Session target: 10-12 minutes.
- Fixed landmarks: `Store`, `Studio`, `Park`, `Station`.
- NPC action whitelist stays bounded.
- Player speech acts stay bounded (`SA_COMPLY`, `SA_INQUIRE`, `SA_FRAME`, `SA_BREAK`).

### 6.2 Runtime constraints
- LLM output is never executed without deterministic runtime validation against current world state.
- Backend always returns a valid decision payload shape.
- Fallback is deterministic and reason-traceable.
- Minecraft diagnostics and runtime compatibility tests must stay green.
- Runtime critical path must remain direct Codex orchestration owned in this repository.

### 6.3 Observability constraints
- Nearby NPC behavior changes must be observable through:
  - block/entity state updates near the active NPC,
  - event evidence (`blockUpdate`, `entitySpawn`, `diggingCompleted`, `blockPlaced`),
  - structured evidence lines (`transport`, `threadId`, `usedFallback`, `reasonCategory`, `warningTier`).
- Runtime evidence extraction must be available from Mineflayer-native telemetry endpoints and scheduler health:
  - `/v1/telemetry/events`,
  - `/v1/telemetry/evidence-pack`,
  - `/health/queue`.
- Runtime evidence collection must not rely on Unity-only telemetry pipelines.

## 7) Acceptance criteria (v0.1)
### 7.1 Core intent verification
1. Mineflayer-driven Minecraft loop completes in 10-12 minutes with defined endings.
2. Codex-driven NPC decision ratio reaches target in live runtime.
3. Three consecutive runs produce non-identical social trajectories.
4. Report/intake/verdict cause chain is readable in player-facing feedback and structured runtime evidence.

### 7.2 Supporting technical verification
5. Codex timeout/failure does not freeze progression.
6. Decision payload remains Schema-valid under normal and failure paths.
7. `sessionId+npcId` continuity is preserved across repeated decisions and reconnect lifecycle events.
8. Diagnostics and compatibility tests pass without exception.
9. Final acceptance run uses repo-owned real Codex runner path (no ad-hoc temp/mock tool runner).
10. Runtime enforces bounded Codex execution and per-NPC one in-flight action processing.
11. Backend cancel/deadline behavior is aligned with Mineflayer action timeout window.
12. Actor workspace continuity is observable and reproducible across repeated cycles.

### 7.3 WS8 release governance verification
13. Gate H decision is derived from Mineflayer Runtime Path Evidence only.
14. Trajectory diversity verification is executed for at least three consecutive runs and linked to reproducible Evidence.
15. Rollback drill result is recorded with reproducible logs and linked from the migration report.
