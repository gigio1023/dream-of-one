# Dream of One - Project Definition (Unity Intent-First v9)

## 0) One-line definition
A Unity social-stealth simulation where NPC society pressure is generated by stateful Codex-driven NPC actors and executed through deterministic world rules.

## 1) Product goal (fixed)
Ship a playable v0.1 slice where the player survives by doing cover work under social scrutiny.

### Primary evaluation question
In Unity play, does a Codex-driven NPC society actually run the pressure loop against the player?

This question is primary.
Platform/framework detail is supporting.

## 2) Core product promise
- Player is not an investigator.
- NPCs and institutions investigate the player.
- Text and social procedure are the danger surface.
- End-state rules remain deterministic and testable.

## 3) What matters most (priority order)
1. Unity play loop runs end-to-end for 10-12 minutes.
2. NPC social actions are generated by Codex cognition path in live loop (target >= 70% non-idle).
3. NPC autonomy continuity is stateful by actor (`npcId`) with thread/workspace memory continuity.
4. Runtime remains stable under load (bounded Codex execution, no process explosion stalls).
5. Report -> intake -> verdict closure is understandable to player.
6. Failure/survival causes are legible in runtime signals and logs.
7. Codex failure never stalls progression (deterministic fallback).

## 4) Technical architecture (supporting, not primary)
### 4.1 Chosen stack for v0.1
- Runtime client: Unity.
- Backend runtime: Node.js 24 LTS.
- Backend server: TypeScript runtime API (current implementation: Node HTTP server).
- Backend language: TypeScript 5.9.
- Agent orchestration: repo-owned direct Codex runtime control plane (no external Agent SDK mediation).
- NPC cognition engine: Codex CLI (`codex`, `codex-reply`).

### 4.2 Runtime model (authoritative)
- NPC logic model: one logical actor state per `sessionId+npcId` (not one always-running OS process per NPC).
- Continuity model: Codex thread continuity via `codex exec` -> `codex exec resume` and persisted actor state.
- Memory model: actor-scoped workspace data (`persona/policy/memory/summary/thread` artifacts) is durable and queryable.
- Execution model: bounded Codex worker pool + per-NPC single-flight mailbox to prevent unbounded child-process fan-out.
- Failure model: timeout/tool/parse errors fall back deterministically without freezing the simulation.

### 4.3 Authority boundary
- Unity authority: world observation, validation, action execution, end-state rules.
- Backend authority: NPC intent brokerage, thread continuity, strict schema validation.
- Codex authority: propose intent only (no direct world mutation).
- Safety authority: deterministic fallback when parse/tool/timeout failures happen.

### 4.4 Runtime guardrail (direction lock)
- v0.1 critical runtime path must not depend on Claude Agent SDK/OpenAI Agent SDK orchestration.
- External SDK research/docs may exist, but acceptance evidence must come from direct Codex runtime path.

## 6) Non-negotiable constraints
### 6.1 Scope constraints
- Session target: 10-12 minutes.
- Fixed landmarks: `Store`, `Studio`, `Park`, `Station`.
- NPC action whitelist stays bounded.
- Player speech acts stay bounded (`SA_COMPLY`, `SA_INQUIRE`, `SA_FRAME`, `SA_BREAK`).

### 6.2 Runtime constraints
- LLM output is never executed without Unity validation.
- Backend always returns a valid decision envelope shape.
- Fallback is deterministic and reason-traceable.
- Unity diagnostics and runtime compatibility tests must stay green.
- Runtime critical path must remain direct Codex orchestration owned in this repository.

## 7) Acceptance criteria (v0.1)
### 7.1 Core intent verification
1. Unity playable loop completes in 10-12 minutes with defined endings.
2. Codex-driven NPC decision ratio reaches target in live runtime.
3. Three consecutive runs produce non-identical social trajectories.
4. Report/intake/verdict cause chain is readable in player-facing feedback and WEL.

### 7.2 Supporting technical verification
5. Codex timeout/failure does not freeze progression.
6. Decision envelope remains schema-valid under normal and failure paths.
7. `sessionId+npcId` thread continuity is preserved across repeated decisions.
8. Diagnostics and compatibility tests pass without exception.
9. Final acceptance run uses repo-owned real Codex runner path (no ad-hoc temp/mock tool runner).
10. Runtime enforces bounded Codex execution and per-NPC single-flight processing.
11. Backend cancel/deadline behavior is aligned with Unity timeout window.
12. Actor workspace continuity is observable and reproducible across repeated cycles.

## 8) Governance
- No new gameplay systems before core intent verification (Section 7.1) is green.
- Backend stack migration is out of scope for v0.1.
- `project.md` and `plan.md` must be updated together when intent/priority changes.
- Terminology must follow `terminology.md` canonical vocabulary for docs and user-facing runtime text.
- Temporary/mock runner may be used only for triage, never as final acceptance evidence.
- "One NPC = one permanent Codex process" is not required; "one NPC = one persistent actor state" is required.
- Any runtime change that increases parallel Codex execution must keep explicit global/per-NPC caps.
- External Agent SDK mediation in decision critical path is out of scope for v0.1.
