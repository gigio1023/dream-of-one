# Dream of One - Project Definition (Unity Intent-First v5)

## 0) One-line definition
A Unity social-stealth simulation where NPC society pressure is generated by Codex CLI cognition and executed through deterministic world rules.

## 1) Product goal (fixed)
Ship a playable v0.1 slice where the player survives by doing cover work under social scrutiny.

### Primary evaluation question
In Unity play, does a Codex-driven NPC society actually run the pressure loop against the player?

This question is primary.
Platform/framework detail is supporting.

## 2) Core product promise
- Player is not an investigator.
- NPCs and institutions investigate the player.
- Text and social procedure are the danger surface.
- End-state gates remain deterministic and testable.

## 3) What matters most (priority order)
1. Unity play loop runs end-to-end for 10-12 minutes.
2. NPC social actions are generated by Codex cognition path in live loop (target >= 70% non-idle).
3. Report -> intake -> verdict closure is understandable to player.
4. Failure/survival causes are legible in runtime signals and logs.
5. Codex failure never stalls progression (deterministic fallback).

## 4) Technical architecture (supporting, not primary)
### 4.1 Chosen stack for v0.1
- Runtime client: Unity.
- Backend runtime: Node.js 24 LTS.
- Backend framework: Fastify 5.x.
- Backend language: TypeScript 5.9.
- Agent orchestration: Claude Agent SDK (TypeScript hooks).
- NPC cognition engine: Codex CLI (`codex`, `codex-reply`).

### 4.2 Authority boundary
- Unity authority: world observation, validation, action execution, end-state gates.
- Backend authority: NPC intent brokerage, thread continuity, strict schema validation.
- Codex authority: propose intent only (no direct world mutation).
- Safety authority: deterministic fallback when parse/tool/timeout failures happen.

## 5) Current implementation truth (2026-02-08)
### 5.1 Implemented and evidenced
- Unity has a working society loop (`observe -> plan -> validate -> execute -> WEL`).
- Unity has pressure/escalation components (`Suspicion`, `Exposure`, report flow, verdict flow).
- TypeScript `npc-runtime` exists with `/v1/npc/decision`, readiness endpoints, thread-store continuity, and deterministic fallback.
- Unity bridge path to `npc-runtime` decision envelope is implemented (`SocietyRuntimeClient`, `SocietyBrain` integration).

### 5.2 Remaining proof gap
- In-editor runtime verification is still required for full proof:
  - Unity diagnostics clean run,
  - PlayMode evidence for transport visibility and failure continuity.

## 6) Non-negotiable constraints
### 6.1 Scope constraints
- Session target: 10-12 minutes.
- Fixed landmarks: `Store`, `Studio`, `Park`, `Station`.
- NPC action whitelist stays bounded.
- Player speech acts stay bounded (`SA_COMPLY`, `SA_INQUIRE`, `SA_FRAME`, `SA_BREAK`).

### 6.2 Runtime constraints
- LLM output is never executed without Unity validation.
- Backend always returns a valid decision envelope shape.
- Fallback is deterministic and reason-traceable.
- Unity diagnostics and runtime contract tests must stay green.

## 7) Acceptance criteria (v0.1)
### 7.1 Core intent proof
1. Unity playable loop completes in 10-12 minutes with defined endings.
2. Codex-driven NPC decision ratio reaches target in live runtime.
3. Three consecutive runs produce non-identical social trajectories.
4. Report/intake/verdict cause chain is readable in player-facing feedback and WEL.

### 7.2 Supporting technical proof
5. Codex timeout/failure does not freeze progression.
6. Decision envelope remains schema-valid under normal and failure paths.
7. `sessionId+npcId` thread continuity is preserved across repeated decisions.
8. Diagnostics and contract tests pass without exception.

## 8) Governance
- No new gameplay systems before core intent proof (Section 7.1) is green.
- Backend stack migration is out of scope for v0.1.
- `project.md` and `plan.md` must be updated together when intent/priority changes.
